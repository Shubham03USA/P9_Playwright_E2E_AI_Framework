================================================================================
PLAYWRIGHT + TYPESCRIPT TEST AUTOMATION FRAMEWORK — COMPLETE EXPLANATION
A "from scratch" guide to understand, explain, and defend the framework
================================================================================

This document explains the entire automation framework file by file, concept by
concept. It is written so that someone who has never seen the project can read it
top to bottom and then confidently explain it in an interview.

================================================================================
1. WHAT IS THIS FRAMEWORK?
================================================================================

This is a Playwright + TypeScript test automation framework. It is built to test
three different layers of an application from one single code base:

   1. WEB UI      -> browser-based end-to-end tests (SwagLabs demo store)
   2. REST API    -> API request/response and JSON-schema tests (FakeStore API)
   3. DATABASE    -> MySQL query utilities for database validation

The framework is designed around three industry-standard principles:

   - Page Object Model (POM)      -> UI locators and actions live in page classes,
                                     never inside the test files.
   - Custom Fixtures              -> Playwright injects ready-to-use page objects
                                     into every test automatically.
   - Externalized Config/Data     -> URLs, credentials, product details, and test
                                     data live in .env and testdata/ files, never
                                     hard-coded in code.

The result is a maintainable, readable, and deterministic test framework where a
test reads like plain English business steps.

================================================================================
2. APPLICATIONS UNDER TEST (IMPORTANT — THERE ARE TWO)
================================================================================

The framework tests TWO different applications. This is a common source of
confusion, so it is called out clearly:

   A) Web UI application (browser):
      - URL:    https://www.saucedemo.com/
      - App:    SwagLabs — a demo e-commerce store
      - Config: WEB_APP_URL, APP_EMAIL, APP_PASSWORD, PRODUCT_NAME, TOTAL_PRICE
      - The UI test logs in with standard_user / secret_sauce, adds a product to
        the cart, and checks out.

   B) API application (HTTP requests):
      - URL:    https://fakestoreapi.com
      - App:    FakeStore API — a public demo REST API
      - Config: API_BASE_URL, FAKESTORE_USERNAME, FAKESTORE_PASSWORD, etc.
      - The API tests cover products, users, carts, and authentication, plus
        JSON-schema validation.

   C) Database (MySQL):
      - Config: DB_HOST, DB_USER, DB_PASSWORD, DB_NAME, DB_PORT
      - A utility (dbClient.ts) connects and runs SQL, used for DB validation.

Knowing this separation matters: the Web tests target SwagLabs, and the API tests
target FakeStore. They are independent applications but are organized in one repo.

4. PREREQUISITES AND SETUP
================================================================================

   To run the framework, the following are needed:
     - Node.js (LTS)
     - npm
     - Playwright browser binaries (installed via `npx playwright install`)

   Setup steps:
     1. Clone the repository.
     2. Run `npm install` (or `npm ci` in CI).
     3. Copy `.env.example` to `.env` (done automatically in CI).
     4. Run `npx playwright install --with-deps` (installs browsers).
     5. Run tests with `npx playwright test`.

   There is also `env_setup.bat`, a Windows batch file that installs all runtime
   dependencies (dotenv, faker, ajv, csv-parse, xlsx, allure, mysql2, etc.) and
   Playwright browsers in one step.

6. DESIGN PRINCIPLES AND PATTERNS
================================================================================

   6.1 Page Object Model (POM)
       - Every web page has a matching class under pages/.
       - The class owns the locators and the actions for that page.
       - Tests never reference CSS selectors or the page directly.
       - Benefit: if a locator changes, it is fixed once in the page object.

   6.2 Custom Fixtures (Dependency Injection)
       - Playwright's `base.extend()` is used to create named fixtures.
       - A test receives page objects as function parameters:
             test('...', async ({ loginPage, productsPage }) => { ... })
       - This removes the need to `new LoginPage(page)` inside every test.
       - The `homePage` fixture also performs the initial navigation.

   6.3 Three-Layer Separation (Web / API / DB)
       - Web:   pages -> fixtures -> tests/web
       - API:   routes + schemas -> tests/api
       - DB:    dbClient -> tests/db
       - Each layer is independent but can be combined in one end-to-end flow.

   6.4 Data & Config Externalization
       - Environment values come from .env via dotenv.
       - Test data comes from testdata/ JSON/CSV/Excel files.
       - Random data is generated by Faker in dataGenerator.ts.

   6.5 Web-First Assertions & Auto-Waiting
       - The framework relies on Playwright's auto-waiting instead of Thread.sleep.
       - Boolean "does this page exist" checks use expect(locator).toHaveText()
         so Playwright waits for the exact expected text (not just visibility).

8. PAGE OBJECTS (pages/ DIRECTORY)
================================================================================

   Every page object follows the same shape:
     - private readonly page: Page
     - a "// Locators" section with private readonly Locator fields
     - a constructor that initializes the locators
     - action methods (return Promise<void> or the next page object)
     - "existence" methods (return Promise<boolean>)

   SwagLabs exposes stable data-test attributes, so locators use [data-test="..."].

   8.1 LoginPage.ts
       Locators:
         - txtUsername -> [data-test="username"]
         - txtPassword -> [data-test="password"]
         - btnLogin    -> [data-test="login-button"]
         - lblError    -> [data-test="error"]
       Methods:
         - isLoginPageExists(): expect(btnLogin).toBeVisible()
         - login(username, password): fills username/password, clicks login,
           returns a new ProductsPage.
         - getErrorMessage(): returns the error text.

   8.2 ProductsPage.ts
       Locators:
         - lblTitle -> .title
       Methods:
         - isProductsPageExists(): expect(lblTitle).toHaveText('Products')
         - clickProduct(productName): finds the inventory item that contains the
           product name, clicks its name link, returns ProductDetailsPage.

   8.3 ProductDetailsPage.ts
       Locators:
         - lblProductName  -> .inventory_details_name
         - lblProductPrice -> .inventory_details_price
         - btnAddToCart    -> [data-test="add-to-cart"]
         - lnkCart         -> [data-test="shopping-cart-link"]
       Methods:
         - isProductDetailsVisible(productName): expect(name).toHaveText(productName)
         - clickAddToCart(): adds the product to the cart.
         - clickCart(): opens the cart, returns CartPage.

   8.4 CartPage.ts
       Locators:
         - lblTitle     -> .title
         - lblItemName  -> [data-test="inventory-item-name"]
         - lblItemPrice -> [data-test="inventory-item-price"]
         - btnCheckout  -> [data-test="checkout"]
       Methods:
         - isCartPageExists(): expect(lblTitle).toHaveText('Your Cart')
         - getItemName(): returns item name text.
         - getItemPrice(): returns item price text.
         - clickCheckout(): returns CheckoutPage.

   8.5 CheckoutPage.ts
       Locators:
         - txtFirstName -> [data-test="firstName"]
         - txtLastName  -> [data-test="lastName"]
         - txtZipCode   -> [data-test="postalCode"]
         - btnContinue  -> [data-test="continue"]
       Methods:
         - fillCheckoutInformation(firstName, lastName, zipCode)
         - clickContinue(): returns CheckoutOverviewPage.

   8.6 CheckoutOverviewPage.ts
       Locators:
         - lblTitle     -> .title
         - lblItemName  -> [data-test="inventory-item-name"]
         - lblItemTotal -> [data-test="subtotal-label"]
         - lblTotal     -> [data-test="total-label"]
         - btnFinish    -> [data-test="finish"]
       Methods:
         - isOverviewPageExists(): expect(lblTitle).toHaveText('Checkout: Overview')
         - getItemName(): returns item name.
         - getItemTotal(): returns subtotal label text.
         - getTotal(): returns grand total label text.
         - clickFinish(): returns CheckoutCompletePage.

   8.7 CheckoutCompletePage.ts
       Locators:
         - lblTitle          -> .title
         - lblCompleteHeader -> [data-test="complete-header"]
       Methods:
         - isCheckoutCompletePageExists(): toHaveText('Checkout: Complete!')
         - getCompleteHeader(): returns 'Thank you for your order!'.

9. CUSTOM FIXTURES (fixtures/pageFixtures.ts)
================================================================================

   Purpose: inject ready-made page objects into tests and share test + expect.

   - Loads dotenv and reads WEB_APP_URL.
   - Defines a PageFixtures type mapping each fixture name to its page class.
   - Uses base.extend() to create the fixtures:
       homePage            -> page.goto(APP_URL), then returns LoginPage
       loginPage           -> new LoginPage(page)
       productsPage        -> new ProductsPage(page)
       productDetailsPage  -> new ProductDetailsPage(page)
       cartPage            -> new CartPage(page)
       checkoutPage        -> new CheckoutPage(page)
       checkoutOverviewPage-> new CheckoutOverviewPage(page)
       checkoutCompletePage-> new CheckoutCompletePage(page)
   - test.afterEach closes the page after each test (if it is still open).
   - Re-exports `expect` so tests import everything from one place:
       import { test, expect } from '../../fixtures/pageFixtures';

   Important note: the "homePage" fixture performs navigation. Because every test
   that requests homePage gets the navigation, the test starts on the app URL
   automatically. The other fixtures simply wrap the same shared `page`.

       - Produces a self-contained, interactive HTML report with:
           - status, severity, duration, and duration-trend charts (Chart.js)
           - test steps with console logs, screenshots, videos, and traces
           - pass rate, filters, and a report history page.
       - Writes output to custom-report/report_<timestamp>.html.

11. TEST DATA AND DATA-DRIVEN APPROACH
================================================================================

   testdata/ contains the same login data in three formats:
     - swaglabs_logindata.json
     - swaglabs_logindata.csv
     - swaglabs_logindata.xlsx

   Each row has:
     - testName  -> human-readable case name
     - email     -> username
     - password  -> password
     - expected  -> "success" or "failure"

   Example rows:
     - Valid login   / standard_user / secret_sauce / success
     - Invalid login / locked_out_user / secret_sauce / failure

   The DataProvider utility reads these files. For a data-driven test, a spec
   loads the file and loops over the rows, producing one independent test per row
   (tagged @datadriven). This keeps test input out of the code.

13. DATABASE LAYER (tests/db/ + dbClient.ts)
================================================================================

   - The tests/db/ folder currently has no committed test files, but the layer
     exists through dbClient.ts.
   - dbClient.executeQuery(sql, params) centralizes connection handling so no
     test writes its own connection code.
   - Connection details come from .env (DB_HOST, DB_PORT, DB_USER, DB_PASSWORD,
     DB_NAME).
   - Typical DB test pattern: insert data -> validate via SELECT -> delete data
     so tests remain repeatable and do not pollute the database.

14. REPORTING (FIVE OUTPUTS)
================================================================================

   On every run the framework produces:

   1. Console "list" reporter  -> immediate pass/fail output in the terminal.
   2. Playwright HTML report   -> reports/ (interactive, with steps + errors).
   3. JUnit XML                -> reports/results.xml (for CI integration).
   4. Custom HTML report       -> custom-report/ (charts, steps, screenshots,
                                  videos, traces, history).
   5. Allure results           -> allure-results/ (generate + open with Allure).

   Failure artifacts are captured automatically:
     - trace: on first retry
     - screenshot: on failure
     - video: retain on failure

   The custom reporter also writes a "live" report during the run (auto-refresh),
   so a developer can watch progress in the browser in real time.

15. THE END-TO-END TEST — COMPLETE WALKTHROUGH
================================================================================

   File: tests/web/end-to-end-shopping-flow.spec.ts
   Tag:  @master @sanity @regression @end-to-end @web

   This single test covers the full customer shopping journey. It imports test +
   expect from the custom fixtures and gets its data from Helper and RandomDataUtil:

     const { email, password } = Helper.getLoginDetails();      // standard_user / secret_sauce
     const { productName, totalPrice } = Helper.getProductDetails(); // Fleece Jacket / $49.99
     const firstName = RandomDataUtil.getFirstName();
     const lastName  = RandomDataUtil.getLastName();
     const zipCode   = RandomDataUtil.getZipCode();

   The flow is wrapped in test.step() blocks so each step shows in the report:

     1)  Open the application          -> homePage fixture navigates; assert login
                                          page is displayed.
     2)  Enter valid username/password -> loginPage.login(email, password).
     3)  Verify successful auth        -> productsPage.isProductsPageExists().
     4)  Select a known product        -> productsPage.clickProduct(productName).
     5)  Open the product details page -> assert the product name matches.
     6)  Add the product to the cart   -> productDetailsPage.clickAddToCart().
     7)  Open the shopping cart        -> productDetailsPage.clickCart().
     8)  Verify the correct product    -> cartPage.getItemName() === productName.
     9)  Verify the product price      -> cartPage.getItemPrice() === totalPrice.
     10) Verify the cart total         -> cartPage.getItemPrice() === totalPrice.
     11) Click Checkout                -> cartPage.clickCheckout().
     12) Enter First/Last/Zip          -> checkoutPage.fillCheckoutInformation(...).
     13) Click Continue                -> assert overview page displayed.
     14) Check Overview details        -> assert item name, item total, grand total.
     15) Click Finish                  -> checkoutOverviewPage.clickFinish().
     16) Verify no errors              -> assert "Checkout: Complete!" and
                                          "Thank you for your order!".

   Why this test is clean:
     - It contains NO locators and NO direct page interaction.
     - Every page action is delegated to a page object.
     - Assertions use Playwright's auto-waiting expect().
     - There are no hard-coded waits (no waitForTimeout / Thread.sleep).

16. TAGGING AND EXECUTION
================================================================================

   Tags are written inside the test title:
     test('... @master @sanity @web', async () => { ... })

   The config default grep is /@master/, so only @master tests run by default.

     @sanity      -> critical smoke tests
     @regression  -> full regression
     @end-to-end  -> full user journeys
     @datadriven  -> data-driven tests
     @api / @db   -> API / database tests

   Example commands:
     npx playwright test                                -> @master tests
     npx playwright test --grep @sanity                 -> @sanity only
     npx playwright test --grep @end-to-end             -> E2E only
     npx playwright test tests/web/end-to-end-shopping-flow.spec.ts
     npm run test:api                                   -> API tests only
     npm run test:web                                   -> Web tests only

     - uses 1 worker
     - uses 2 retries

18. KEY PLAYWRIGHT CONCEPTS TO MENTION
================================================================================

   - Auto-waiting: Playwright waits for elements to be actionable before acting.
   - Web-first assertions: expect(locator).toBeVisible()/toHaveText() auto-wait.
   - Built-in locators: getByRole/getByText/getByLabel/getByPlaceholder and
     attribute selectors (this project uses data-test attributes).
   - Fixtures: dependency-injected setup/teardown shared across tests.
   - APIRequestContext: the `request` fixture does REST testing in the same runner.
   - Tracing: on-first-retry captures a full trace to replay failures.
   - Projects: run the same tests against chromium / firefox / webkit.
   - Test steps (test.step): group actions into reportable, readable steps.
   - Tags/grep: filter which tests run without editing the code.

================================================================================
19. FLOW OF A SINGLE TEST (WHAT HAPPENS UNDER THE HOOD)
================================================================================

   This is the important mental model to explain in an interview.

   When you run one Web test:

   1. Playwright reads playwright.config.ts.
   2. The runner loads the matching test file (grep filter).
   3. Playwright creates a browser context and page (built-in fixtures).
   4. Custom fixtures from pageFixtures.ts are built:
        - homePage calls page.goto(WEB_APP_URL).
        - every other fixture wraps the same page in a page-object class.
   5. The test function receives all requested fixtures as parameters.
   6. The test body runs step by step, delegating each action to a page object.
   7. Each page-object action uses auto-waiting locators, so no manual sleeps.
   8. Assertions use web-first expect() and retry until they pass or time out.
   9. On completion, afterEach closes the page.
   10. Reporters write console, HTML, JUnit, custom HTML, and Allure outputs.
   11. If the test failed, traces/screenshots/videos are captured for debugging.

   For an API test, the flow is the same except:
       - It uses the `request` fixture (not `page`).
       - It builds URLs from the Routes object.
       - It validates status codes, bodies, and JSON schemas (AJV).

20. COMMON INTERVIEW QUESTIONS AND TALKING POINTS
================================================================================

   Q: Why Playwright over Selenium?
   A: Playwright has native auto-waiting, web-first assertions, built-in fixtures,
      built-in API testing (request fixture), multi-browser support, tracing, and
      better handling of modern web apps. No separate WebDriver binary is needed.

   Q: Why TypeScript?
   A: Type safety catches mistakes at compile time, gives better IDE autocomplete,
      and makes the framework more maintainable at scale.

   Q: What design pattern do you use?
   A: Page Object Model, plus custom fixtures for dependency injection, plus a
      layered structure (Web / API / DB) and externalized data/config.

   Q: How do you avoid flaky tests?
   A: No hard-coded waits; use auto-waiting and web-first assertions; stable
      data-test locators; retries only in CI; consistent viewport; and traces and
      videos on failure for debugging.

   Q: How is test data managed?
   A: Externalized in .env (config/credentials) and testdata/ (JSON/CSV/Excel).
      Random data is generated with Faker. Data-driven tests loop over rows.

   Q: How do you do API testing in the same framework?
   A: Use Playwright's request fixture with a centralized Routes object, plus AJV
      JSON-schema validation.

   Q: How does reporting work?
   A: Five outputs: console list, Playwright HTML, JUnit XML, a custom HTML report
      with dashboard charts, and Allure.

   Q: How does CI work?
   A: GitHub Actions runs on push/PR/manual trigger, installs dependencies and
      browsers, creates .env, runs the selected suite/browser/mode, and uploads
      reports as artifacts. CI mode is headless with 1 worker and 2 retries.
